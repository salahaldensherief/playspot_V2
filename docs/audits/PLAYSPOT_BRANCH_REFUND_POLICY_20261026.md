# Branch booking refund policy — 26 October 2026

Status: **Draft configuration and eligibility only; do not merge or deploy independently.** The product owner specified that each branch owner chooses a refund deadline and percentage. No payment gateway exists. Cancelling a booking is not evidence that a manual refund was paid.

The Draft migration adds append-only, private policy versions for each lounge/branch. An active, unbanned owner can set the cutoff in minutes before the booked start (0–43,200) and refundable percentage (0–100, two decimal places) through an idempotent RPC. Another branch owner, a customer, or a revoked owner cannot change it. Public read access exposes only the active branch's current percentage/cutoff, never the configuring actor. New bookings snapshot the policy version at creation; later policy edits do not rewrite older bookings. Older bookings with no snapshot require manual review.

The private eligibility helper uses the stored booking cancellation timestamp, booked start and lounge timezone. It returns the snapshot percentage only when cancellation occurred by the cutoff before play. A started session yields 0; missing snapshot or start data yields manual review. It deliberately does **not** calculate a refund amount, create a payment obligation, mark a refund pending/completed, or move money. Those operations require the verified collection movement contract and separate authorization/evidence of actual manual return.

In the isolated production-equivalent schema, the rollback-only synthetic fixture passed 3/3: branch A 120 minutes/50%, branch B 30 minutes/25%, an A edit to 60 minutes/75% preserved the earlier booking's 50% snapshot, a repeated operation returned the same version, conflicting replay and cross-branch/disabled-owner/customer writes were rejected, an eligible cancellation returned 50%, and a cancellation after a 30-day cutoff returned 0%. No synthetic lounge, booking or policy rows remained after rollback. This is policy eligibility verification, **not** a refund or reconciliation test.

Before release: integrate branch settings into Dashboard owner UI; display the policy to Mobile customers before reservation; implement refund obligation and verified manual return against canonical money movements; reconcile commission, custody, shifts and payouts; test duplicate and concurrent refund requests, full/partial/no refund, old clients and authenticated browser flows. Staging must verify migration and rollback/recovery with historical bookings lacking a snapshot. No production database was modified.
