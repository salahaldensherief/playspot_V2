Additional read-only function/trigger inspection found a concrete cross-path conflict to reproduce after restore. Deployed `payments` has the `guard_partial_cash_payment` trigger. Once a booking has a row in `private.cash_collection_receipts`, its trigger rejects a `payments` insert/update unless the same transaction records that booking in `private.cash_collection_context`. The canonical `collect_booking_cash_partial` → `private.apply_partial_cash_collection` path sets that context. Deployed `complete_booking_payment` does **not** set it, yet upserts `payments`; therefore a checkout attempt with an outstanding canonical partial-cash receipt reaches `CASH_LEDGER_REQUIRES_CANONICAL_COLLECTION` rather than collecting the balance. Dashboard `confirmCashPayment` calls `apply_booking_discount` first, then `complete_booking_payment` in a second RPC, so the first discount can remain committed when the second call hits this guard. This is a static contract-path finding from deployed definitions and current Dashboard source, not a representative runtime reproduction. It makes the combined atomic checkout test a release gate, not an optional enhancement.
