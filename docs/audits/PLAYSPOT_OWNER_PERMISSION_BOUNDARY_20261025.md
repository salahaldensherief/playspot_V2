# Owner permission write boundary — 25 October 2026

Status: Draft, targeting `dev`. No production schema or data change.

The authorized schema-only snapshot matched the target's 3,607 public/private catalog entries before Draft migrations. The same disposable PostgreSQL 17 restore was reused here. Its `staff_permissions_manage_scoped` RLS policy allowed any lounge manager to write their own permission override. `lounge_role_permissions_write` also allowed direct role-template writes, bypassing the narrower `update_role_permission` RPC. Direct `lounge_staff` writes let a manager assign themselves `lounge_owner`. The RPC restricted manager target roles but did not check whether the manager held a permission before granting it to cashiers or staff. The isolated snapshot contained no per-employee permission mutation RPC or permission-specific audit trail.

This Draft migration revokes direct authenticated/anon DML on both permission tables and `lounge_staff`, adds `set_staff_permission` for active owners/super-admins to grant or revoke an active employee's individual permission, and blocks self/cross-lounge grants. It constrains manager template delegation to permissions the manager currently holds. Both RPC paths write a server-side `permission_audit_logs` row; authenticated users have read-only access, scoped to their own active lounge ownership. The functions use a fixed search path, authenticated actor checks and a per-permission transaction lock before recording the previous value. The Dashboard's existing role-template editor calls `update_role_permission`, so that path remains available with tighter delegation. Dashboard Draft PR #84 adds the owner per-employee editor; it depends on this backend PR.

The existing `get_staff_permissions` reads the employee profile's primary lounge, which is ambiguous for multi-branch staff. The Draft adds `get_lounge_staff_permissions(lounge_id, target_user_id)` with explicit owner, target membership and lounge checks. The Dashboard owner editor uses this scoped read; the old RPC remains unchanged for existing clients.

The final branch-scoped version of the isolated authorization suite passed **3/3 runs**, including owner read and denied manager/foreign-owner reads. With this permission migration also present in the disposable database, the atomic cash checkout regression passed all **12 scenario groups** in one additional integration run.

No fixture rows remain after rollback.
