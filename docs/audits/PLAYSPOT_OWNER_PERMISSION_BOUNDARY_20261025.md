# Owner permission write boundary — 25 October 2026

Status: Draft, targeting `dev`. No production schema or data change.

The authorized schema-only snapshot matched the target's 3,607 public/private catalog entries before Draft migrations. The same disposable PostgreSQL 17 restore was reused here. Its `staff_permissions_manage_scoped` RLS policy allowed any lounge manager to write their own permission override. `lounge_role_permissions_write` also allowed direct role-template writes, bypassing the narrower `update_role_permission` RPC. The RPC restricted manager target roles but did not check whether the manager held a permission before granting it to cashiers or staff. The isolated snapshot contained no per-employee permission mutation RPC or permission-specific audit trail.

This Draft migration revokes direct authenticated/anon DML on both permission tables, adds `set_staff_permission` for active owners/super-admins to grant or revoke an active employee's individual permission, and blocks self/cross-lounge grants. It constrains manager template delegation to permissions the manager currently holds. Both RPC paths write a server-side `permission_audit_logs` row; authenticated users have read-only access, scoped to their own active lounge ownership. The functions use a fixed search path, authenticated actor checks and a per-permission transaction lock before recording the previous value. The Dashboard's existing role-template editor calls `update_role_permission`, so that path remains available with tighter delegation. A per-employee owner editor is not yet wired into either client.

The migration was applied only to `playspot_financial_restore_20261025`. The guard-protected test `supabase/tests/financial_contract/owner_permission_exact_schema.cjs` passed **3/3 consecutive runs**. Each run creates synthetic users and lounges inside a rollback transaction, then checks: direct staff/template table writes denied; manager self grant and delegation beyond own permission denied; foreign-lounge owner denied; owner self grant denied; owner grant and revoke persisted within the transaction; owner can see the two audit entries; a foreign owner cannot see them; and a manager cannot delete audit history. No fixture rows remain after rollback.

Open gates: this is a narrow permission-write fix, not the full requested employee role and approval system. Verify every client and integration that writes these tables before release. The owner still needs a per-employee UI, a complete permission catalogue for transfers, refunds, discounts and offline devices, and a reviewed delegation policy for administrators. Audit coverage for other financial mutations remains separate. Run this migration against a production-equivalent staging environment with the final client builds and a recovery rehearsal before any release. Do not merge or deploy without the owner's explicit approval.
